# Описание проекта для резюме и собеседований

> **Главное правило:** проект — самостоятельная учебная работа, выполненная с помощью ИИ-ассистента.
> Не называй его коммерческим опытом, не пиши «работал QA в компании». Сила проекта — в глубине,
> которую ты можешь объяснить, а не в громких словах.
>
> Цифры ниже — реальные на момент создания. Если ты изменишь проект — обнови их.
> **Пункт про CI пиши только после того, как сам увидел зелёный запуск на GitHub.**

## 1. Строка в резюме (раздел «Проекты»)

**FinGuard QA Automation Suite** — учебный проект, Python · pytest · httpx · Playwright · PostgreSQL · GitHub Actions
[github.com/<логин>/finguard-qa-automation](https://github.com/)

- Разработал автотесты для банковского REST API (FastAPI + PostgreSQL): 90 тест-кейсов — функциональные,
  негативные, граничные, проверки БД, идемпотентность и параллельные переводы.
- Покрыл веб-интерфейс 17 UI-тестами на Playwright с Page Object Model, без `sleep`, со скриншотами и
  трассировками при падении.
- Нашёл и задокументировал баг (HTTP 500 на id вне диапазона INTEGER), написал регрессионный тест.
- Проверил эффективность тестов ручным мутационным анализом: внедрённые ошибки (гонка, отсутствие
  проверки прав, off-by-one, неатомарный перевод) обнаруживаются тестами.
- Настроил CI в GitHub Actions: PostgreSQL service container, Ruff, отчёты и артефакты. *(после проверки)*

*Самостоятельный учебный проект, выполнен с использованием ИИ-ассистента.*

## 4. Рассказ на 3 минуты

**1. Контекст (20 с).** «Хотел портфолио, которое показывает не количество тестов, а инженерный подход.
Выбрал банковский домен, потому что там понятные и жёсткие требования: деньги не должны появляться,
исчезать или списываться дважды».

**2. Что тестируется (20 с).** «Сервис на FastAPI и PostgreSQL: регистрация, JWT-авторизация, счета
в трёх валютах, пополнение, переводы, история. Плюс простой веб-интерфейс».

**3. Подход (40 с).** «Начал с рисков: двойное списание, гонки, доступ к чужим счетам, ошибки с деньгами.
Под них — пирамида: основа — API-тесты, сверху немного UI. Каждый тест создаёт свои данные, поэтому
тесты независимы. После каждой отклонённой операции проверяю не только код ответа, но и что в базе
ничего не изменилось. Контрактные тесты — строгими схемами, написанными отдельно от приложения».

**4. Самое интересное (50 с).** «Две вещи. Первая — параллельные переводы. 10 потоков одновременно
переводят по 30 со счёта со 100. Я не знаю, какие три пройдут, но знаю, что ровно три — проверяю
инвариант, а не порядок, поэтому тест стабильный и без sleep. Когда я убрал из кода блокировку строк,
прошли все десять переводов — тест это поймал.
Вторая — атомарность. Через monkeypatch я роняю перевод *после* списания, проверяю, что внутри
транзакции списание уже было, а после сбоя в базе всё откатилось».

**5. Результат (30 с).** «107 тестов, все проходят. Нашёл баг: id больше предела INTEGER давал 500 —
описал, написал падающий тест, исправил. Чтобы проверить сами тесты, внедрял в код типичные баги —
тесты их ловили. Один «выживший» случай оказался защитой второго уровня — это тоже разобрал».

**6. Честность и выводы (20 с).** «Проект учебный и сделан с ИИ-ассистентом. Ограничения я описал
в known issues — например, токен не отзывается при выходе. Дальше хочу добавить нагрузочное тестирование».

## 5. Вопросы, которые вероятно зададут (подготовься)

Полный список с ответами — `interview_questions_ru.md`. Самые вероятные:

1. Почему для чужого счёта 404, а не 403?
2. Как сделать тест параллельных запросов стабильным?
3. Что такое идемпотентность? Что будет при повторе неудачного перевода?
4. Почему деньги — не float?
5. Зачем проверять БД, если API вернул 201?
6. Как вы проверили, что тесты ловят баги?
7. Как отлаживать упавший UI-тест в CI?
8. Что бы вы улучшили?
9. Какую часть сделали вы, а какую ИИ? → Ответ честный и конкретный: что разбирал, что менял, какие задания
   выполнил сам (`practical_exercises_ru.md`).
10. Покажите тест и измените его прямо сейчас. → Будь готов к live-coding: добавить кейс в parametrize,
    написать новый негативный тест, найти причину падения.

## 6. Чего НЕ говорить

- ❌ «Протестировал банковскую систему» → ✅ «учебный сервис в банковском домене».
- ❌ «100% покрытие» → покрытие кода не измерялось.
- ❌ «Настроил CI/CD» — пока не видел зелёный запуск.
- ❌ «Сам всё написал» — если это не так. Честность про ИИ — плюс, разоблачение на live-coding — провал.
