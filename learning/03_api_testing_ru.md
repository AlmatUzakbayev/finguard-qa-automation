# 03. API-тестирование: разбор каждого теста

## Часть 1. Минимум теории

### HTTP-запрос и ответ
```
POST /api/transfers HTTP/1.1                    <- метод + путь
Authorization: Bearer eyJhbGciOi...             <- заголовки
Idempotency-Key: 9f1c...
Content-Type: application/json

{"from_account_id": 1, "to_account_id": 2, "amount": "30.00"}   <- тело

HTTP/1.1 201 Created                            <- статус
{"id": 7, "from_account_id": 1, ... }           <- тело ответа
```

### Статус-коды в проекте

| Код | Значение | Когда у нас |
|---|---|---|
| 200 OK | успех | чтение, логин, пополнение, **повтор** перевода с тем же ключом |
| 201 Created | создан ресурс | регистрация, счёт, новый перевод |
| 401 Unauthorized | «кто ты?» — нет/плохой токен | любой защищённый эндпоинт без валидного токена |
| 404 Not Found | нет ресурса | несуществующий **или чужой** счёт |
| 409 Conflict | конфликт с текущим состоянием | email занят; ключ идемпотентности с другим телом |
| 422 Unprocessable | данные не прошли проверку | валидация, недостаточно средств, разные валюты |
| 500 | ошибка сервера | **всегда баг** (см. BUG-001) |

**401 vs 403:** 401 — «не знаю, кто ты» (аутентификация). 403 — «знаю, но нельзя» (авторизация).
Для чужих счетов у нас 404, а не 403 — см. вопрос «почему 404» ниже.

### JWT за 1 минуту
Токен = `header.payload.signature` (base64). В payload: `sub` (id пользователя), `exp` (срок).
Сервер проверяет подпись своим секретом (`JWT_SECRET`). Подделать payload нельзя — подпись не сойдётся.
Посмотреть содержимое: вставь токен на jwt.io (только учебные токены!).

### Как устроены API-тесты проекта
- `FinGuardApi` (`tests/support/api_client.py`) — тонкий клиент: методы возвращают **сырой**
  `httpx.Response`. Клиент не решает, что такое «ошибка», — это решает тест.
- Шаблон теста **Arrange → Act → Assert** (подготовка → действие → проверка), разделены пустыми строками.
- После каждого отклонённого действия проверяем, что **ничего не изменилось**.

## Часть 2. Разбор основных тестов

Для каждого: **сценарий → ожидание → что проверяет assert → как сломать → как диагностировать**.
«Как сломать» — правка в коде приложения в учебных целях. **После эксперимента верни код**
(`git checkout app/services.py` или Ctrl+Z).

### 2.1 `test_transfer_moves_money_between_users` (test_transfers.py)

- **Сценарий:** у пользователя 1000.00, он переводит 250.50 другому пользователю с описанием.
- **Ожидание:** `201`, в ответе правильные счета/сумма/описание; баланс отправителя `749.50`,
  получателя `250.50`.
- **Assert:**
  - `assert_status(response, 201)` — перевод создан;
  - `transfer["amount"] == "250.50"` — сумма строкой с 2 знаками (не float!);
  - балансы проверяются **отдельными запросами** — ответ «201» сам по себе не доказывает, что деньги
    реально перешли.
- **Как сломать:** в `app/services.py` закомментируй `target.balance += req.amount`.
- **Что увидишь:** упадёт последняя строка: получатель имеет `"0.00"` вместо `"250.50"`.
  Деньги «исчезли» — именно такой баг ловят проверки после действия.
- **Диагностика:** сообщение assert покажет фактический баланс; проверь в БД:
  `SELECT id, balance FROM accounts ORDER BY id DESC LIMIT 5;`

### 2.2 `test_transfer_with_invalid_amount_is_rejected_and_changes_nothing` (7 кейсов)

- **Сценарий:** перевод суммы `-10.00`, `0`, `0.00`, `0.001`, `abc`, `NaN`, `null`.
- **Ожидание:** `422 VALIDATION_ERROR`, ошибка относится к полю `amount`; баланс 100.00; строк в БД нет.
- **Assert:**
  - `assert_error(response, 422, "VALIDATION_ERROR")` — статус, единый формат ошибки, код;
  - `["body", "amount"] in [e["loc"][:2] ...]` — ошибка именно про `amount`, а не про что-то другое
    (иначе тест мог бы пройти «по случайной причине»);
  - `db.balance(...) == Decimal("100.00")` и `transfers_between(...) == []` — побочных эффектов нет.
- **Как сломать:** в `app/config.py` поставь `min_amount = Decimal("0")`.
- **Что увидишь:** кейсы `zero` и `zero-with-decimals` упадут — сервер ответит **500**: валидация
  пропустила 0, а в БД сработал `CHECK (amount > 0)`. Интересно: деньги всё равно не ушли —
  база защитила. Но 500 — это баг.
- **Диагностика:** `reports/server.log` → трейсбэк `CheckViolation ... ck_transactions_amount_positive`.

### 2.3 `test_transfer_with_insufficient_funds_is_rejected_and_changes_nothing`

- **Сценарий:** баланс 50.00, перевод 50.01 (на копейку больше).
- **Ожидание:** `422 INSUFFICIENT_FUNDS`, оба баланса без изменений.
- **Как сломать:** удали в `services.py` блок `if source.balance < req.amount: raise ...`.
- **Что увидишь:** вместо 422 придёт **500** — сработает `CHECK (balance >= 0)` в БД.
  Вывод для собеседования: *ограничение в БД — последняя линия обороны, но проверка в коде
  нужна, чтобы клиент получил понятную ошибку, а не 500.*

### 2.4 `test_cannot_transfer_from_someone_elses_account` (безопасность, BOLA/IDOR)

- **Сценарий:** злоумышленник знает id счёта жертвы и пытается перевести деньги себе.
- **Ожидание:** `404 "Source account not found"`, деньги жертвы на месте, у злоумышленника 0.
- **Как сломать:** в `services.py` замени `if source is None or source.owner_id != user.id:`
  на `if source is None:`.
- **Что увидишь:** тест упадёт: `201` вместо `404` — **кража удалась**. Это проверено (мутация M3).
- **Почему это важно:** BOLA (Broken Object Level Authorization) — риск №1 в OWASP API Top 10.

### 2.5 `test_foreign_account_is_indistinguishable_from_missing_one` (4 кейса)

- **Сценарий:** для 4 действий (счёт, баланс, история, пополнение) сравниваем ответ на **чужой**
  счёт с ответом на **несуществующий**.
- **Assert:** `foreign.json() == missing.json()` — ответы идентичны.
- **Почему 404, а не 403?** 403 сообщил бы «счёт есть, но не твой» — злоумышленник смог бы перебором
  узнать, какие id существуют (enumeration). 404 не раскрывает ничего.
- **Как сломать:** в `get_own_account` убери `or account.owner_id != user.id` → тест покажет
  `200` с чужим балансом.

### 2.6 `test_profile_rejects_missing_or_invalid_token` (6 кейсов)

| Кейс | Что подаём | Ожидаемая причина |
|---|---|---|
| no-header | ничего | `Missing Authorization header` |
| garbage-token | `Bearer not.a.jwt` | `Invalid token` |
| wrong-scheme | `Basic <token>` | `Authorization header must be 'Bearer <token>'` |
| foreign-signature | токен, подписанный чужим ключом | `Invalid token` |
| expired-token | токен с `exp` в прошлом (подписан правильным ключом!) | `Token has expired` |
| deleted-user | валидный токен для несуществующего id | `Invalid token` |

- **Как тест делает просроченный токен:** тест знает `JWT_SECRET` (тот же, что у сервера) и сам
  подписывает токен с `exp = now - 1 минута`. Это честная проверка: подпись верна, истёк только срок.
- **Как сломать:** в `app/security.py` в `jwt.decode(...)` добавь `options={"verify_exp": False, ...}`
  → упадёт кейс `expired-token` (сервер пустит с просроченным токеном).

### 2.7 `test_login_failure_does_not_reveal_which_part_is_wrong`

- Неверный пароль и неизвестный email дают **одинаковое** сообщение. Иначе можно проверить,
  зарегистрирован ли email (user enumeration).
- **Как сломать:** в `routers/auth.py` раздели условие и для `user is None` верни
  `"User not found"` → упадёт кейс `unknown-email`.

### 2.8 `test_transfer_amount_boundaries` (test_boundaries.py, 5 кейсов)

Анализ граничных значений: проверяем **на границе, чуть ниже и чуть выше**.

| Кейс | Баланс | Сумма | Ожидание |
|---|---|---|---|
| minimum-amount | 100.00 | 0.01 | 201, остаток 99.99 |
| amount-equals-balance | 100.00 | 100.00 | 201, остаток 0.00 |
| balance-plus-one-cent | 100.00 | 100.01 | 422 |
| maximum-amount | 1 000 000.00 | 1 000 000.00 | 201 |
| maximum-plus-one-cent | 1 000 000.00 | 1 000 000.01 | 422 |

- **Как сломать:** в `services.py` замени `<` на `<=` в проверке баланса.
- **Что увидишь (проверено, мутация M4):** упадут `amount-equals-balance` и `maximum-amount` —
  нельзя перевести «всё до копейки». Классический off-by-one, который ловят только граничные тесты.

### 2.9 `test_over_limit_transfer_fails_validation_even_with_enough_money`

Отделяет две причины отказа: при балансе 2 000 000 перевод 1 000 000.01 отклонён из-за **лимита**
(`less_than_equal`), а не из-за баланса. Без этого теста `maximum-plus-one-cent` мог бы проходить
по неправильной причине (просто нехватка денег).

### 2.10 `test_retry_with_same_idempotency_key_returns_original_transfer`

- **Сценарий:** клиент отправил перевод, не получил ответ (сеть), повторил с **тем же** ключом.
- **Ожидание:** первый `201`, второй `200` + заголовок `Idempotent-Replayed: true`, тело **такое же**;
  списано **один раз** (75.00), строка в БД **одна**.
- **Как сломать:** в `execute_transfer` замени `existing = _find_by_key(db, user, key)` на
  `existing = None`.
- **Что увидишь (мутация M2):** повтор вернёт **500** — второе списание упрётся в UNIQUE-ограничение БД.
  Деньги не спишутся дважды (база спасла), но клиент получит ошибку вместо результата.

### 2.11 `test_successful_responses_match_contract` (test_contract.py)

- Проходит основной сценарий и проверяет **каждый** ответ строгой схемой из
  `tests/support/contracts.py` (`extra="forbid"` — лишнее поле = ошибка).
- **Почему схемы написаны заново, а не импортированы из `app/schemas.py`?** Если разработчик
  переименует поле в приложении, импортированная схема «переименуется» вместе с ним, и тест ничего
  не заметит. Контракт — это **ожидание клиента**, оно должно жить отдельно.
- **Как сломать:** добавь в `UserOut` (`app/schemas.py`) поле `password_hash: str` → контрактный
  тест упадёт с `Extra inputs are not permitted` (утечка хеша пароля поймана).

### 2.12 `test_invalid_account_id_is_rejected_by_validation` — регрессионный тест BUG-001

История бага — в `docs/known_issues.md`. Тест был написан **до исправления** и падал (500).
- **Как сломать:** в `routers/accounts.py` замени `account_id: AccountId` на `account_id: int`
  в `get_account` → кейсы `int32-max-plus-1` и `huge` снова дадут 500.

## Часть 4. Ручное исследование API (exploratory)

Автотесты проверяют то, что ты **придумал**. Ручное исследование находит то, что ты **не придумал**.
Так найден BUG-001: перебор граничных значений id в URL через `curl`.

```bash
TOKEN=...   # из ответа /api/auth/login
curl -i http://127.0.0.1:8000/api/accounts/2147483648 -H "Authorization: Bearer $TOKEN"
```
Идеи для самостоятельного исследования: очень длинное описание (141 символ), unicode/emoji в имени,
`amount` числом vs строкой, `limit=0`, `limit=101`, `offset=-1`, пустое тело, неверный JSON,
`Content-Type: text/plain`.
