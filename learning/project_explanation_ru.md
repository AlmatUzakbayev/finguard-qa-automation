# Объяснение проекта по компонентам

Для каждого компонента: **что делает → зачем → почему так → что может сломаться → как отлаживать →
как объяснить работодателю** (готовая фраза, но перескажи своими словами).

## Часть 1. Тестируемое приложение (app/)

### 1.1 `app/config.py` — настройки
- **Что:** все настройки в одном классе `Settings`; значения берутся из переменных окружения или `.env`.
- **Зачем:** один и тот же код работает локально, в тестах и в CI с разными БД и секретами.
- **Почему так:** `pydantic-settings` сам читает и проверяет типы (`ACCESS_TOKEN_EXPIRE_MINUTES=abc` → ошибка при старте).
- **Может сломаться:** забыли задать `DATABASE_URL` → приложение пойдёт в БД по умолчанию.
- **Отладка:** `python -c "from app.config import get_settings; print(get_settings())"`.
- **Работодателю:** «Конфигурация через переменные окружения по принципам 12-factor; бизнес-лимиты
  (мин./макс. сумма) вынесены в одно место, тесты на границы опираются на них».

### 1.2 `app/models.py` + `alembic/` — схема БД
- **Что:** таблицы `users`, `accounts`, `transactions` и ограничения: `CHECK (balance >= 0)`,
  `CHECK (amount > 0)`, `UNIQUE (initiator_id, idempotency_key)`.
- **Зачем ограничения в БД, если есть проверки в коде:** код может содержать ошибку; ограничение в БД
  — последняя линия обороны. Мутационные проверки это показали: при удалённой проверке баланса в коде
  деньги **не ушли в минус** — сработал CHECK (но клиент получил 500).
- **Почему `NUMERIC(18,2)`:** точная десятичная арифметика, без ошибок float.
- **Отладка:** `psql` → `\d accounts`.
- **Работодателю:** «Инварианты защищены на двух уровнях: валидацией в приложении для понятных ошибок
  и constraint-ами в БД как гарантией».

### 1.3 `app/schemas.py` — валидация входа/выхода
- **Что:** Pydantic-модели запросов и ответов.
- **Важные решения:**
  - `Amount`: `>= 0.01`, не более 2 знаков, `<= 1 000 000.00`;
  - `extra="forbid"` — неизвестное поле = 422 (защита от mass assignment: `"is_admin": true`);
  - `MAX_DB_ID` — id не больше предела `INTEGER` (исправление **BUG-001**);
  - деньги в ответе — строка `"100.00"`.
- **Может сломаться:** ослабили валидацию → данные доходят до БД → 500.
- **Работодателю:** «Валидация на границе системы: всё, что не проходит схему, получает 422 с указанием поля».

### 1.4 `app/security.py` — пароли и токены
- **Пароли:** PBKDF2-HMAC-SHA256, соль, 600 000 итераций (рекомендация OWASP). Хеш хранит число
  итераций, поэтому их можно менять, не ломая старые пароли. `hmac.compare_digest` — сравнение за
  постоянное время (нет timing-атаки).
- **Токены:** JWT HS256 с `sub` (id) и `exp` (срок). Проверка: подпись, срок, обязательные поля.
- **Почему тесты используют 1000 итераций:** на машине разработки 1 хеш = 2,5 с; тесты регистрируют
  сотни пользователей. Корректность хеширования проверяется (регистрация + вход), меняется только «цена».
- **Работодателю:** «Я заметил, что тесты идут 10 минут, профилировал и нашёл причину — намеренно медленное
  хеширование. Сделал параметр, тесты ускорились в 3,5 раза, продакшен-значение не тронуто».

### 1.5 `app/deps.py` — текущий пользователь
- **Что:** достаёт токен из `Authorization: Bearer ...`, проверяет, находит пользователя. Иначе 401
  с конкретной причиной и заголовком `WWW-Authenticate: Bearer`.
- **Может сломаться:** новый эндпоинт без `CurrentUser` → доступен без входа. Ловит
  `test_protected_endpoints_require_authentication`.

### 1.6 `app/services.py` — **сердце проекта: перевод**
Порядок действий в `execute_transfer`:
1. `SELECT ... FOR UPDATE ORDER BY id` — заблокировать оба счёта в фиксированном порядке.
2. Найти перевод с тем же `Idempotency-Key` → вернуть его (или 409, если тело другое).
3. Проверки: счёт отправителя мой? получатель существует? валюты равны? денег хватает?
4. Списать, зачислить, `flush` (UPDATE отправлены, но не закоммичены).
5. Записать транзакцию.
6. `COMMIT` — всё сразу. Ошибка до этого → откат всего.

- **Что может сломаться и какой тест поймает** (проверено внедрением багов):

| Баг | Тест, который упадёт |
|---|---|
| нет `FOR UPDATE` | `test_parallel_transfers_never_overdraw_the_account`, `test_opposite_parallel_transfers...` |
| нет проверки ключа | `test_retry_with_same_idempotency_key...`, `test_parallel_retries...` |
| нет проверки владельца | `test_cannot_transfer_from_someone_elses_account` |
| `<=` вместо `<` | `test_transfer_amount_boundaries[amount-equals-balance]` |
| commit после списания | `test_transfer_is_rolled_back_completely_if_it_fails_midway` |

- **Отладка:** `reports/server.log`; в `psql`: `SELECT * FROM pg_locks WHERE NOT granted;` — кто кого ждёт.
- **Работодателю:** «Перевод атомарный, с пессимистичной блокировкой строк в фиксированном порядке
  против дедлоков, идемпотентный по ключу клиента. Каждое из этих свойств покрыто тестом, и я проверил,
  что тесты падают, если свойство убрать».

### 1.7 `app/errors.py` — единый формат ошибок
- Все ошибки: `{"code": "INSUFFICIENT_FUNDS", "detail": "..."}`; валидация ещё и `errors: [...]`.
- **Зачем `code`:** клиент (и тест) проверяет код, а не текст — текст можно перевести/переформулировать.

### 1.8 `frontend/` — веб-интерфейс
- Статические HTML + чистый JavaScript, без сборки. Отдаётся тем же FastAPI.
- **Почему не React:** задача — тестировать, а не писать фронтенд. Меньше кода — меньше мест для ошибок.
- `data-testid` на всех важных элементах — договор с тестами.
- Токен в `sessionStorage` (ограничение описано в known_issues).

## Часть 2. Тестовый фреймворк (tests/)

### 2.1 `tests/conftest.py`
- **Что:** проверяет БД, применяет миграции, запускает сервер на свободном порту, создаёт пользователей и счета.
- **Почему сервер — отдельный процесс, а не TestClient:** (1) тесты идут по настоящему HTTP, как клиент;
  (2) конкурентные тесты требуют настоящего многопоточного сервера; (3) тот же сервер нужен UI-тестам.
- **Может сломаться:** БД не запущена → понятное сообщение и код выхода 3 вместо 100 одинаковых ошибок.
- **Работодателю:** «Одна команда `pytest` поднимает всё сама — одинаково локально и в CI».

### 2.2 `tests/support/api_client.py`
- Методы возвращают сырой `httpx.Response`. **Клиент не прячет ошибки** — решение принимает тест.
- `transfer()` сам генерирует `Idempotency-Key`, если не передан.

### 2.3 `tests/support/assertions.py`
- `assert_status`, `assert_error` — при падении печатают метод, путь, статус и тело ответа.

### 2.4 `tests/support/db.py` — `DbInspector`
- Прямые SQL-запросы для проверок, которые API не покажет: точные значения, отсутствие строк, сверка с журналом.

### 2.5 `tests/support/contracts.py`
- Независимое описание контракта API строгими Pydantic-моделями. Не импортирует `app/schemas.py` — намеренно.

### 2.6 `tests/ui/pages.py`, `tests/ui/conftest.py`
- Page Objects, фикстура `logged_in_page`, таймаут `expect` 10 с.

## Часть 3. Как рассказать архитектуру за 30 секунд

> «Это учебный банковский API на FastAPI и PostgreSQL с простым веб-интерфейсом. Я написал два набора
> тестов. API-тесты на pytest и httpx — 90 кейсов: функциональные, негативные, граничные, проверки
> базы, идемпотентность и параллельные переводы. UI-тесты на Playwright с Page Object — 17 кейсов.
> `pytest` сам поднимает миграции и сервер, в GitHub Actions — PostgreSQL как service container.
> Нашёл и исправил баг с 500-й ошибкой на больших id, а чтобы убедиться, что тесты чего-то стоят,
> внедрял в код типичные ошибки — гонки, пропущенные проверки прав, off-by-one — и смотрел, что тесты их ловят».
